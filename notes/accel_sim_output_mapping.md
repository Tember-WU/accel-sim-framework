# Accel-Sim example_output.txt Output Mapping

This note explains the output generated by:

```bash
gpu-simulator/bin/release/accel-sim.out \
  -trace example_trace/kernelslist.g \
  -config ./gpu-simulator/gpgpu-sim/configs/tested-cfgs/SM86_RTX3070/gpgpusim.config \
  -config ./gpu-simulator/configs/tested-cfgs/SM86_RTX3070/trace.config \
  > example_output.txt
```

Overall flow:

```text
main.cc
  -> accel_sim_framework(argc, argv)
  -> initialize GPGPU-Sim performance model
  -> parse example_trace/kernelslist.g
  -> process MemcpyHtoD commands
  -> parse example_trace/kernel-1.traceg header
  -> launch trace kernel
  -> cycle-level simulation
  -> print kernel statistics
  -> exit
```

Input file:

- `example_trace/kernelslist.g`

Meaning:

- The first 8 commands in `kernelslist.g` are host-to-device copies.
- `parse_memcpy_info()` extracts the device address and byte count.
- `m_gpgpu_sim->perf_memcpy_to_gpu(address, count)` models the effect of the copy in the simulated memory hierarchy.

Detailed behavior:

- `trace_parser::parse_commandlist_file()` only treats lines starting with `MemcpyHtoD` as CPU-to-GPU memory-copy commands. GPU-to-CPU copies are ignored in this parser path.
- `trace_parser::parse_memcpy_info()` splits one command line into three fields:

```text
MemcpyHtoD, device_address, byte_count
```

- `accel_sim_framework::parse_commandlist()` prints `launching memcpy command : ...` and calls:

```cpp
m_gpgpu_sim->perf_memcpy_to_gpu(addre, Bcount);
```

- `gpgpu_sim::perf_memcpy_to_gpu()` only runs when `-gpgpu_perf_sim_memcpy` is enabled. This option is registered in `memory_config::reg_options()` with the description `Fill the L2 cache on memcpy`, and its default value is `1`.
- The function walks the copied byte range in 32-byte chunks. For each 32B sector, it creates a sector mask, decodes the address, finds the target memory partition/sub-partition, and calls `force_l2_tag_update()`.
- The final update calls `baseline_cache::force_tag_access()`, which directly fills the L2 tag array:

```cpp
void force_tag_access(new_addr_type addr, unsigned time,
                      mem_access_sector_mask_t mask) {
  mem_access_byte_mask_t byte_mask;
  m_tag_array->fill(addr, time, mask, byte_mask, true);
}
```

So in trace-driven Accel-Sim, this memcpy path mainly forces the L2 tag array to look as if these addresses were just touched by a copy operation.

### Simulator Memcpy vs Real GPU Memcpy

Real GPU behavior:

- A real `cudaMemcpyHostToDevice` or `cudaMemcpyAsync(..., cudaMemcpyHostToDevice)` actually moves data from CPU host memory to GPU device memory.
- It uses the CUDA runtime/driver, PCIe or NVLink, and usually a GPU copy/DMA engine.
- It writes real bytes into GPU DRAM.
- It has real latency and bandwidth cost.
- For async copies, stream ordering and overlap with kernels/copies matter.
- Depending on architecture and copy path, the operation may also affect L2 cache state.

Trace-driven simulator behavior:

- The trace already contains the kernel's memory addresses and instructions, so the simulator usually does not need the actual data values.
- `MemcpyHtoD` does not copy host bytes into a simulated data array in this path.
- It does not fully model PCIe/NVLink traffic.
- It does not fully model copy-engine queueing, bandwidth, overlap, or stream synchronization.
- It does not count a realistic memcpy duration as part of kernel execution time.
- Its main modeled effect is updating L2 tag state so the following kernel sees a cache state closer to what could happen after a real host-to-device copy.

Short version:

```text
Real GPU memcpy: moves real data.
Trace-driven Accel-Sim memcpy: mainly warms/updates simulated L2 cache tags for the copied GPU address range.
```

Example output:

```text

Warp Occupancy Distribution:
Stall:144094    W0_Idle:101082    W0_Scoreboard:486197    W1:3264 ... W32:228021
single_issue_nums: WS0:67830    WS1:67881    WS2:64668    WS3:64668

```

Code:

- `gpu-simulator/gpgpu-sim/src/gpgpu-sim/shader.cc:724-744` prints this block.
- `gpu-simulator/gpgpu-sim/src/gpgpu-sim/shader.cc:1040-1052` increments the `W1` through `W32` buckets using `active_count()`.
- `gpu-simulator/gpgpu-sim/src/gpgpu-sim/shader.cc:1558-1566` increments the special `W0_Idle`, `W0_Scoreboard`, and `Stall` buckets.
- `gpu-simulator/gpgpu-sim/src/gpgpu-sim/shader.cc:1548-1552` increments `single_issue_nums` and `dual_issue_nums`.

Important distinction:

- `W1` through `W32` are not warp IDs. They are active-lane-count buckets for issued warp instructions.
- `W32:228021` means 228,021 issued warp instructions had all 32 lanes active.
- `W1`, `W9`, `W23`, etc. mean some issued warp instructions had only that many active lanes, usually because of divergence or predication.
- `W0_Idle` means no valid instruction was available to issue, or a control hazard left the scheduler idle.
- `W0_Scoreboard` means a valid instruction existed but was not ready because scoreboard dependencies were not satisfied, commonly RAW dependencies from previous ALU or memory operations.
- `Stall` means an instruction was ready but could not issue because of pipeline/resource pressure.
- `gpu_reg_bank_conflict_stalls = 0` counts register-file bank-conflict stalls. This is separate from L1 cache bank conflict statistics such as `gpgpu_n_l1cache_bkconflict`.

The array layout is:

```text
shader_cycle_distro[0]  -> W0_Idle
shader_cycle_distro[1]  -> W0_Scoreboard
shader_cycle_distro[2]  -> Stall
shader_cycle_distro[3]  -> W1
shader_cycle_distro[4]  -> W2
...
shader_cycle_distro[34] -> W32
```

`single_issue_nums` and `dual_issue_nums` are indexed by warp scheduler inside one SM, not by SM id. In this config `-gpgpu_num_sched_per_core 4`, so the output has `WS0` through `WS3`. `single_issue_nums` counts cycles where that warp scheduler issued one instruction; `dual_issue_nums` counts cycles where it issued more than one. In this run all dual-issue counters are zero.

### Why The Issue Distribution Says Shader 0

The line:

```text
ctas_completed 51, Shader 0 warp_id issue ditsribution:
```

is printed by `gpgpu_sim::shader_print_scheduler_stat()`. That function intentionally prints the warp issue distribution from one sampling shader core:

```cpp
const unsigned scheduler_sampling_core = m_shader_config->gpgpu_warp_issue_shader;
```

The option is registered in `gpu-simulator/gpgpu-sim/src/gpgpu-sim/gpu-sim.cc:481-487`:

```text
-gpgpu_warp_issue_shader 0
```

So by default, the detailed `warp_id issue distribution` is sampled from shader core 0 only. This does not mean the whole simulation only used shader 0. Other statistics in the same section, such as `ctas_completed`, `gpgpu_n_tot_thrd_icount`, `gpgpu_n_tot_w_icount`, memory instruction counts, and the cache/memory stats, are aggregate statistics across the simulated GPU unless their label explicitly says they are per-core or sampled.

For this run, the kernel has 51 CTAs and the GPU config has 46 shader clusters/SMs. `CTA/core = 2` is a per-SM residency limit, not a promise that every SM gets two CTAs. Because there are only 51 CTAs total, the launch can fill roughly one CTA on each of 46 SMs, with only 5 additional CTAs available beyond that. Therefore most SMs do not need to host two CTAs for this small kernel, even though the resource limit allows up to two.
